00Engineering plan

What the backend will be.

The login you're testing runs entirely inside one browser — no server, no real accounts. This is the plan to make it real: where data lives, how someone truly signs in (email and Google), and what a developer builds. Read it as the blueprint you hand to whoever writes the server.

01 · The shift

From a demo to a real product.

The prototype fakes the parts that matter most for safety. Here's exactly what changes when there's a true backend behind it.

Today · prototype

Lives in the browser

  • Accounts saved in localStorage on one device only
  • Passwords stored as plain text — not safe
  • Google button is a visual stub
  • Nothing syncs phone ↔ laptop
  • Clear the browser and the account is gone
Next · real backend
  • Accounts in a database, reachable from any device
  • Passwords hashed (bcrypt) — never stored readable
  • Real Google sign-in via OAuth
  • Progress syncs everywhere, instantly
  • Email verification, password reset, backups

03 · How signing in works

Two doors, one reader.

Whether they use a password or Google, both paths end the same way — a verified user and a secure session. The same person can use either and land in the same account.

@ Email & password

  1. Reader submits name, email, username, password.
  2. Server hashes the password with bcrypt and stores only the hash.
  3. A verification email goes out; they click to confirm.
  4. On login, server compares the hash and issues a session token (JWT or cookie).
  5. Every request after carries that token — that's how the app knows who they are.

G Continue with Google

  1. Reader taps Continue with Google, picks their account.
  2. Google sends back a signed token proving who they are (OAuth 2.0).
  3. Server verifies it, then finds or creates a matching user.
  4. An auth_identity row links that Google account to the user.
  5. Same session token is issued — identical from here on.

Why it's done this way

The server never sees a Google password, and never stores your readers' passwords in readable form. If the database ever leaked, there'd be no passwords to steal — only hashes that can't be reversed. This is the baseline standard; anything less shouldn't take real signups.

05 · What it's built with

A simple, boring stack — on purpose.

Nothing exotic. These are well-worn, well-documented tools a single developer can run cheaply, so the ministry isn't locked to one specialist.

Database
Postgres
Holds the four tables. Rock-solid, free, runs anywhere.
Easiest start: Supabase (Postgres + auth + Google login bundled)
Server / API
Node + Express
Serves the endpoints above. Same language as the front-end.
Or: the backend built into Supabase / Firebase
Auth & Google
OAuth + JWT
Google sign-in and secure sessions, the standard way.
Managed option: Auth0 or Clerk handle it for you

The shortcut worth considering

A tool like Supabase gives you the database, password login, and Google sign-in out of the box — much of section 03 becomes configuration instead of code. For a ministry launching lean, that can turn months of backend work into a couple of weeks. Worth weighing against building it custom.

06 · Getting there

The order of operations.

Phase 1Now → prototype

Prove the experience

The login + dashboard you're testing. Refine how it should feel — this is free to change and costs nothing to get right before any server exists.

Phase 2Before launch

Stand up the backend

A developer builds the four tables, the auth flows, and the endpoints above — or wires Supabase. The existing screens get pointed at the real server instead of the browser.

Phase 3Launch

Real readers, real accounts

Email verification, password reset, and Google sign-in all live. Progress syncs across devices. Now it's safe to take genuine signups — and to add giving.

Phase 4Later

Grow

More series, reading streaks, reminders, a real app shell. Each rides on the same foundation — nothing here needs to be rebuilt.

This is a plan, not yet a build. When you're ready, it becomes the brief a developer works straight from — every table, flow, and endpoint already decided.
